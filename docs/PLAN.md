# Fresh Market 移交后执行方案

**版本**：plan-2026-11-14  
**目标**：让接手人能在不依赖个人记忆的情况下，安全核对当前状态、选择一个明确范围、完成可回读的副本同步，并知道何时停止。

## 1. 交付目标

1. 保持科迈 SaaS 只读，所有副本写入走 Lovrabet 标准模型 API。
2. 以 capture、batch、window 和 read-back 证据组成可恢复的同步闭环。
3. 把列表覆盖、详情覆盖、数据截至时间、成本/库存/会员/营销覆盖分开表达。
4. 让同步状态、经营指标和页面只读消费同一份自有副本。
5. 将未验收、暂停和历史证据从当前执行路径中隔离。

## 2. 分阶段计划

| 阶段 | 目的 | 主要动作 | 通过条件 | 失败处理 |
|---|---|---|---|---|
| P0 接手核对 | 建立当前基线 | `capabilities`、`status`、`gaps show`、运行时检查、离线测试 | 输出带时间的本地审计；无锁冲突；映射可用 | 停止，不访问源站，不改状态 |
| P1 单流小窗口 | 验证当前版本可运行 | 选一个已放行流，先 `plan`，再执行一个已结束日 | 源范围、行数、摘要、回读、同 capture 零源重放一致 | 保留 capture，按 OPERATIONS 恢复或放弃 |
| P2 受控追赶 | 扩大到明确历史窗口 | 逐流、逐窗口执行；每次限制源操作预算 | 每个窗口有完成证据；缺口和 partial 明确记录 | 不推进连续检查点，开独立核对 |
| P3 业务消费 | 对齐页面和指标 | 核对数据集关系、BFF 口径、页面数据截至时间 | 页面只读；指标版本、coverage、warnings 可见 | 回退页面入口，不改变源或业务副本 |
| P4 新能力评审 | 扩展详情/对象/新流 | 补稳定键、映射、事务、回读、重复运行和真实小样本 | 独立 acceptance 证据并更新能力表/文档 | 保持 paused/no-go，不绕过网关 |

P0 和 P1 是移交验收的最小闭环；P2–P4 不是默认上线承诺。

## 3. 当前优先级

### 优先做

- 先确认 5 条 accepted 列表流的当前窗口和私有工件是否连续可恢复。
- 将历史 `purchase-receive-history` 的哈希/映射问题保持为明确 no-go，补齐证据后再评审。
- 让页面和经营指标展示最新业务日期、数据截至时间和覆盖提示。
- 维护运行时 OpenCLI 副本与仓库适配器的一致性检查。

### 暂不做

- 不启用零售订单详情/支付补采。
- 不启用 `retail-promote-sharing` 的通用增量，不把促销物理表迁移当作源端完成。
- 不启动常驻 supervisor、OS 调度或多机并发。
- 不以旧 MySQL 写入器、裸 SQL 或任意批量接口替代标准网关。

## 4. 每阶段必须留下的证据

- 运行时间、操作者、流、日期窗口和源/数据中心范围。
- source operation 预算与实际逻辑操作数；未知 HTTP 数量保持未知。
- capture ID、batch ID、窗口证据、数据库回读和同 capture 重放结果。
- 列表/详情覆盖、空日、partial、未解决缺口和暂停原因。
- 失败时的固定错误类别和私有工件路径；不得写入凭据、签名 URL 或原始业务明细。

## 5. 变更门槛

下列任一变更需要更新 `ARCHITECTURE.md`、`OPERATIONS.md` 和本方案，并补离线测试：

- 源筛选、时间字段、门店范围或稳定键变化。
- 数据集代码、主键、租户隔离或 SQL/BFF 指标口径变化。
- acceptance 流、暂停流或详情预算变化。
- 锁、限流、恢复、批次大小或回读策略变化。
- 页面对“最新”“完整”“毛利”“库存”“会员”“促销”的表述变化。

## 6. 责任分工

| 角色 | 责任 |
|---|---|
| 数据所有者 | 持有科迈账号；如需改源数据，由本人在官方界面处理 |
| 同步维护者 | 运行 P0–P2、维护工件和本地审计，不绕过安全边界 |
| 数据中心维护者 | 维护数据集、关系、BFF、SQL 和权限；只写自有副本 |
| 业务验收人 | 确认窗口、覆盖和指标是否满足业务用途，不把估算当财务结论 |

任何角色都不能授权本项目修改或删除科迈 SaaS 数据。
