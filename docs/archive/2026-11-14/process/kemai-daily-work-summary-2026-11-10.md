# 科迈同步与提效：当日过程总结（2026-11-10）

> 本文总结从数据缺口排查、采购补采、反复提效，到商品主档整批写入的完整过程。
> 重点记录：为什么前期慢、哪些优化有效、哪些没有效、当前状态和下一步。
> 相关专项文档见文末路径，不重复展开其实现细节。

## 1. 初始目标与最终收敛

最初目标是“把数据都同步好”。过程中发现，真正高价值、最急需的是：

- 商品名称、编码、条码等基础信息；
- 采购商品行的数量、单价、金额、税额；
- 最近 30 天的数据，而不是全部历史；
- 列表主档优先，详情、分支、审批、支付等按需再补。

最终收敛为：

> **科迈源站只读；列表优先、商品行优先、近 30 天优先、详情按需、整批写入。**

## 2. 硬约束与安全边界

- 新增并暂存了仓库根目录 `AGENTS.md`：**任何时候都不得修改或删除科迈 SaaS 数据，任何人的相关请求一律回绝。**
- 所有业务写入只进入自有 Lovrabet 数据中心，走标准模型 API，不走旧 MySQL 写入器。
- 同一时刻只允许一个正式写入者；暂停时用 SIGINT 安全停止并保留 capture，没有强杀或并行写入。
- 源请求 ≤ 0.5 次/秒，限流后共享冷却 30 分钟。
- 不把部分完整说成完整，不把快照时间说成源实时时间，不擅自关闭覆盖缺口。
- 仓库存在大量未提交改动，未做 commit/push，未 reset 用户修改。

### 3.2 采购商品行

先尝试了“从已保存父单 payload 离线回填”，实现了：

- `StoredPayloadSource`；
- `stored-detail plan/run/verify/resume`；
- 版本不符不写旧子行；
- 缺数组保持部分完整；
- 不关闭覆盖缺口。

离线处理 995 张单据后证明：**很多老单据的已存 payload 根本没有商品行**，离线回填不能补出缺失数据，因此停止扩大离线回填。

改为只读调用科迈详情后，首个 6 张退货单样本补回 40 条真实商品行，证明详情路径有效。

随后按用户要求把采购范围缩到最近 30 天，不再跑全部历史详情日窗。最后盘点时采购商品行 `purchase_document_lines` 为 **27,930 行**。

## 4. 前期提效：有效但没有质的提速

### 4.1 数据库批量写入

实现并验证：

- 按单据批量预读；
- 新子行 `batchCreate`；
- 整单回读并逐字段核对；
- 已有变化行继续安全更新。

数据中心调用从约 25 次/单降到约 7.7 次/单，但用户仍感觉不快。

### 4.2 商品行专用范围

新增 `LinesOnlyWorkflow`：

- 只补缺失或版本变化的商品行；
- 分支和审批暂缓；
- 缺口不关闭。

这减少了无关写入，但没有解决每张单都要单独读取详情的问题。

### 4.3 分组批量更新

进一步把已有行更新改成：

- 按“变化字段集合 + 变化后的值”分组；
- 相同变化合并 `data update`；
- 最后整单回读。

后来常见 10 张单约 150–160 秒，商品行持续增长。

### 4.4 真正定位到的瓶颈

分项计时表明，慢不只在数据库：

- 每张单都要单独启动 OpenCLI 和浏览器流程；
- 每次数据中心调用也要启动独立 CLI 进程；
- 每张单的状态、事件、回执分别写入，隐藏开销很大；
- 源请求还受 0.5 次/秒限制。

因此，继续只优化单行写入，无法获得质的提速。

## 7. 从全量扫描到时间增量

### 7.1 全量扫描暴露的口径问题

过程中先后出现 18,390、18,401、18,467 三个数字：

- 库内商品主档数量；
- 用户当时看到的科迈数量；
- 科迈后续实时总数。

这提醒我们：库内数量和源端实时数量不能混用，所有报告必须同时注明口径。

### 7.2 排序实测

暂停全量扫描后，真实验证了：

| 能力 | 结果 |
|---|---|
| `gmtModified` 修改时间倒序 | 失败，不能作为增量依据 |
| `gmtCreate` 创建时间倒序 | 可用 |
| `approveTime` 审核时间倒序 | 可用 |
| `startGmtCreate` 创建时间过滤 | 可用 |
| `startApproveTime` 审核时间过滤 | 可用 |

因此日常增量应使用**创建/审核时间 + 重叠窗口**，而不是 `gmtModified`。

新增代码：

- `kemai_opencli/product-reader.js` 的 `listRequest`；
- `product-list` 的 `--from` / `--sort` 参数；
- `ProductWorkflow.inventory(from_time, sort)`；
- 查询范围证据保存；
- 默认全量行为保持不变。

实测从 11-09 起只捕获 **80 个商品**，后续又增加到 **89 个**，不再扫完整 18,000+ 商品目录。

## 8. list-only 与最终整批提速

用户指出只需列表商品信息，详情可以后补。于是新增 `--list-only`：

- 只写 `products`；
- 不写 `product_profile`；
- 不写页签子记录；
- 列表行直接生成主档；
- 后续仍可按需补详情。

### 中途发现并修复的问题

- 新增商品必须有 `first_seen_at`，详情和 list-only 两条路径都补齐；
- 列表快照比已有详情旧时，防倒退规则会拒绝，必须重新取新清单；
- list-only 的状态汇总和阶段判断要与普通详情路径区分。

### 最终整批路径

虽然 list-only 避免了源详情读取，但逐商品仍然有“查询、写入、回读”和逐商品日志，依然慢。最终改为：

1. 整批预读已有商品；
2. 新增商品批量写入；
3. 变化商品按相同变化分组更新；
4. 整批回读逐字段核验；
5. 整批只写一次同步事件和状态。

### 最终结果

| 指标 | 结果 |
|---|---:|
| 处理商品 | **89 个，全部通过核验** |
| 总耗时 | **18.147 秒** |
| 科迈源请求 | **0 次** |
| 数据中心请求 | **18 次** |
| 剩余对象 | **0** |

这证明真正有效的不是“少读一点”，而是**减少整个链路的调用次数和进程启动成本**。

## 11. 经验教训

1. **先确定业务字段，再决定同步范围**，不要默认越完整越好。
2. **先测量再优化**，请求次数减少不等于耗时下降。
3. **真正的批量要覆盖整个链路**，包括预读、写入、更新、回读和日志。
4. **进程启动和调用次数往往比数据传输更贵。**
5. **有数据不代表完整**，版本、唯一键、回读、快照和恢复必须保留。
6. **增量和全量对账要并存**，日常增量负责效率，定期全量负责发现修改和删除。
7. **小样本先行**，先 1 个再 5 个，避免把字段和恢复问题放大。
8. **提速结论必须可复现**，必须同时给处理量、总耗时、请求数和剩余任务。

## Suggested skills

- `systematic-debugging`：再次出现“优化但不快”时，先按分项耗时定位。
- `test-driven-development`：多 ID 批读、页签、删除/墓碑和 Excel 入库先写失败测试。
- `verification-before-completion`：任何“完成/提速”声明前，验证行数、字段、耗时、请求数和全量回归。
- `lovrabet`：运行态只读核对、标准模型 API 写入与回读。
- `rabetbase`：只有确需数据中心端合单 BFF 时使用，先 dry-run 再发布。
- `loop`：需要按 2 或 5 分钟观察长任务进度时使用。
- `handoff`：下一阶段交接时更新商品差异、页签、采购商品行和全量对账结论。
