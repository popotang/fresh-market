# 科迈同步体系后续开发计划（交给 DeepSeek 执行）

本计划接续[已完成的标准接口交付](kemai-standard-api-delivery-2026-11-08.md)和[操作指引](kemai-pipeline-operations-2026-11-08.md)。它是开发与验收要求，不代表下列链路已经上线。以执行时的 `kemai_syncctl.py capabilities`、DB 状态及最新审计证据判断实际能力；旧运行报告中的数字是当时快照。

根目录的脚本、日志、状态、样本和历史文档整理，按[仓库清理计划](kemai-repository-cleanup-plan-2026-11-08.md)同步执行；它要求先盘点引用与活动进程，再分类搬迁和清理。

## 目标与不变约束

目标是让科迈 OpenCLI 专注取源，Lovrabet CLI 与数据中心标准接口专注读写，Python 编排负责确定性的全量补录、小时级增量、断点和核对，Skill 根据证据选择有界任务。每类数据要能查源观测时间、最近成功入库时间、连续完整覆盖、详情覆盖与未补齐缺口。停机后按逐日证据识别缺口，不按定时器错过的次数机械重放。

1. 业务写入只用 `filter`、`aggregate`、`batchCreate`、`update`、事务等标准模型 API；不得以 Custom SQL 或旧 `kemai_commerce_sync.py` 的 MySQL 写入冒充新架构。DDL 可单独审查并通过已授权的数据库工具执行。
2. 保持单机共享写锁、服务端每流控制行锁、源站 0.5 次/秒逻辑操作上限与限流 30 分钟冷却。不能并行启动旧 supervisor 和新服务。多机运行前必须另做集中租约/fencing 验收。
3. 已完成的两条零售流不得产生重复数据或回退覆盖。零售详情/支付仍处于用户暂停状态；采购与商品的开发不解除该暂停。
4. 原始页、查询范围、导出任务 ID、摘要和批次回执保持不可变。源分页中断不能拼接另一时间点的页；已采完源但写入中断，应先查询回执、恢复同一 capture。
5. `last_success_at` 是入库时间，`source_observed_at` 是源观测时间；空日必须有真实源空页证据。列表、详情、派生数据和 Excel 导入分别标注覆盖级别。源 HTTP 请求数未在 gate 层计量时输出 `null`，不得用 OpenCLI 调用数充当精确请求数。

## 当前起点与边界

`kemai_pipeline/js/sync_gateway.mjs` 目前只放行 `retail-sales`、`retail-orders`；四条采购流虽然列在 `specs`，写操作会被 `STREAM_ACCEPTANCE_REQUIRED` 拦下。采购的 `capture-page`、`purchase-detail`、`purchase-receive-history-export-start` 与 `normalize.py` 已存在，但不能据此称采购已迁移。现有采购表是 `purchase_documents`、三张子表、`purchase_document_detail_state` 及 `purchase_receipt_history_lines`；详情旧链路已出现：订单缺 `approves`，收货/退货缺 `branchs`。采购列表 `totalRecord` 过去不可靠，只能在未验证导出时声明“单轮唯一键数”，不能声称独立源总数。

零售两条流的真实回归、接口容量、并发和事务证据详见交付记录。它们提供公共内核的证据，**不自动证明采购的真实载荷、复合键、子表写入或历史 Excel 映射安全**。执行前须实时检查常驻进程与活动 capture；本计划不自动启用服务。

## P1：采购三类单据列表迁移（先做）

### P1.1 冻结源契约和日期口径

- 对 `purchase-orders`、`purchase-receipts`、`purchase-returns` 各取少量真实样本，记录页面请求参数、`dateType` 的实际语义、机构范围、默认隐藏筛选、分页总数语义、`id`/`gmtCreate`/`gmtModified` 的存在与类型。使用现有 OpenCLI 和共享 gate；不要用浏览器自动化做常规验证。
- 明确“30–60 分钟增量按哪个不可漏的时间字段取源”。若源列表只支持制单日且旧单可修改，当前日+前一日复访并不足以覆盖任意旧单修订：定义可验证的 `gmtModified` 游标或有界历史重核策略；在证据不足前，能力说明标成“新增/迟到覆盖，旧日修订未保证”，不得承诺完全增量。
- 新版 `capture-page` 对采购也必须固定/验证查询范围，清理已知 UI 临时筛选，并拒绝未知非空筛选或机构变化。页与页的 `query_scope` 完全一致；源键重复或总数变化即放弃本次 offset 快照。若 `totalRecord` 返回 0 但页有数据，标记未知而非 0。
- 根据已验证时间口径调整 `CAPABILITIES.date_field`、`normalize.py` 和 DB 索引。索引先用标准 API 只读聚合评估，再单独执行 DDL 并复测；不要直接复制零售的上传时间假设。

### P1.2 接入标准网关与逐日窗口

- `purchase_documents` 的业务唯一键是 `(tenant_id,document_kind,source_document_id)`。`source_capture` 仍按 `(tenant_id,stream,source_key)` 保存；订单/收货/退货相同源 ID 不得互相覆盖。检查 `prepare_ingestion`、`writeRows`、最终按日聚合都携带 `document_kind`。字段映射必须用真实样本证明，特别是状态、金额的 1/10000 缩放、关联单号和时间。
- 同一 capture/sequence 产生固定批次 ID；同 ID 同摘要返回原回执，不同摘要拒绝。业务父行、原始捕获、批次回执同事务；最终窗口、成功事件、流状态同事务。失败/限流日志不得推进成功水位。
- 单轮列表以唯一源键数、保存行数和 DB 日计数三方核对。源 `totalRecord` 只有确认可靠时才作为第四方；不能把 DB 行数称为独立源总数。空日要有真实空页证据。大窗口应在写入前估算 100,000 行/5,000 批上限并有明确拒绝输出。
- 先在测试副本/隔离数据集做重复、冲突、并发、强制回滚和 48 KB/200 行边界；再对**已有采购业务行**做事务内试写并强制回滚、读回完全一致。每条流各选一个小的已结束真实日，用标准接口重放并核对键集、摘要、日期计数，随后源预算 0 重放同 capture。逐条验收后才加入 `accepted_streams`。

### P1.3 采购详情独立队列

- 列表窗口只声明 `list_only`；详情使用 `purchase_document_detail_state` 按稳定父单据 ID 排队和续跑。详情采集必须经 `opencli kemai purchase-detail` 和共享 gate，不能让列表每日重扫带动所有旧单详情请求。列表更新后只把新增、内容变化或明确欠缺的单据加入队列。
- 按文档类型和真实响应建立数组契约。`details` 缺键/非数组是详情失败；`branchs`、`approves` **缺键**表示源未提供，记 `partial` 和缺口，不清空已有子表。**显式空数组**仅在该接口确实返回且父单身份/版本核对通过时，才可作为“该子项为 0”并清理旧行。不要把所有三种单据都强制要求三个数组。
- 对每个实际返回的数组，子行以 `(document_id,source_line_id/source_key)` 幂等写入。父行、所返回子集、详情状态、缺口事件在同一事务；子项缺失时不触碰原有子表。真实返回的详情父 ID/单号/类型与列表父行冲突时失败并保留证据。对已有子行的删除/替换必须限定**该数组已完整返回**，并验证外键与重复键。
- 状态至少区分 `pending/success/partial/failed`，保存源版本、尝试次数、成功/失败时间、各数组计数与缺项。`partial` 不能升级为 `full_detail`；重试成功后再关闭对应缺口。旧详情已存在时先做 DB 键/摘要承接，不因迁移而批量重抓；旧子表与新标准接口不能双写。
- 小样本至少覆盖三种单据各 5 张、缺 `branchs`、缺 `approves`、显式空数组、详情中断、同单据并发重试、已有子行不被缺键清空、详情版本变化、父子事务回滚。详情吞吐单独测量并给出上限；在源限流或服务繁忙时允许列表新鲜度下降，状态页应如实显示。

## P2：历史已审核收货及 Excel 首录

- 先核对 `purchase-receive-history` 的 `approveTime`、`dateType=1`、查询范围、分页与已知 11 个缺口窗。`history_key()` 当前以 `sheetNo + 规范化 sequence + itemCode/itemId` 生成 SHA-256；用真实 API 与 Excel 同单行对照，证明 Excel 能取得**相同稳定键**，并验证 `source_document_id` 与原单据的关联。若缺字段或有键碰撞，停止导入该窗口并记映射缺口，不造临时行号。
- 分页与 Excel 必须走同一 `normalize`、批次回执和窗口提交逻辑。先对一日小样本交叉导入，两种来源的同一业务键、金额、数量和摘要进行一致性核对；文件按任务号、SHA-256、任务原始时间和查询范围留证。24 小时复用任务只能标为复用，不能声明新的导出快照。
- Excel 优先用于历史大窗口；页数小且源总数可核对时可用分页。何时切换由实测行数/页数/文件大小/源操作预算决定，不能用固定阈值掩盖 Excel 缺列。缺口逐窗补录，完成后核对源唯一键、DB 键、金额/数量汇总，并只推进实际完成的日期证据。

## P3：商品与关联档案

- 在采购四流验收后，接入商品清单、基本详情、14 类页签及机构/部门/类别/品牌/单位。先证明清单覆盖账号可见范围且 UI 筛选已清除，再用源 ID+版本/摘要构造变化对象队列。详情与每个页签有独立状态、断点和缺口；历史价格须真实分页至末页。
- 主表、详情、类型子表按对象/页签事务写入；明确子记录稳定键、空数组与缺键语义，避免清空旧关系。商品与供应商/类别/品牌/单位关联以源 ID 保存，展示名称由维表关联读取。
- 商品 Excel 首录需证明与 API 稳定键等价，验证小样本交叉导入与历史数据无重复后，再开放大批量。204,836 个旧页签待处理是旧运行报告中的快照，不作为本轮实时总量或完成承诺。

## P4：零售派生、历史核对与持续运行

- 将零售流水→订单行派生迁入标准接口，核对来源稳定键、孤儿、重复和金额；零售原详情/支付继续保持暂停，直到用户另行明确恢复。
- `history check --scope db` 保持零源请求；另实现真正的只读 `--scope source`，只做有界单轮源对账并记录其成本。`history fill` 根据已验证缺口选择分页/Excel；不能把补录伪装成只读检查。
- 增量触发周期 30/60 分钟，当前上传日临时快照优先，已结束日按源延迟规则复访；旧日复访的频率要可配置，避免每轮全量扫描昨天。停机/限流恢复从 `sync_pipeline_windows` 的连续逐日证据和活动 capture 规划最多 N 个缺日，优先恢复原 capture，再补小窗口；超预算留待下次。
- 全部链路逐条验收后才扩充 `kemai_pipeline_service.py` 的 stream 白名单；单机守护/开机自启、页面最后同步时间展示、跨机租约分别作为独立发布项。页面明确显示列表/详情/派生覆盖和源观测时间，不把入库时间显示成源实时数据。

### 暂停与回退规则

遇 HTTP 200 业务码限流、429 或弹窗，立即记录并共享冷却 30 分钟；不反复探测。导出提交结果未知只按精确采集文件名/任务号恢复，不能盲目重建。源页中断、详情字段契约不符、键碰撞、批次回执不明、DB 日计数冲突时，不推进完整窗口。先保留工件和日志、查回执与活动 capture，再决定恢复或新建快照。回退前停新执行者并确认旧写入者互斥；不得手改窗口、回执或水位以制造成功。
