# 科迈小时级增量与停机追赶设计

> 2026-11-08 方案与首阶段实现。本文最初的「尚未启动」记录是设计时快照；**最新执行状态以 [交付与验收记录](kemai-sync-delivery-2026-11-08.md#十二2026-11-08-受控执行与核对) 为准**。本轮真实源 `once`、页签小样本与状态页发布已完成，新零售服务试启后按用户目标澄清停止；旧日常 supervisor 仍暂停。任何新源请求继续维持全局最多 0.5 次/秒和限流后 30 分钟冷却。

## 首阶段已实现：零售交易

`kemai_live_sync.py` 现在提供 `migrate / plan / once / supervise`。`once` 先抓当天两条零售流，按源 ID upsert，生成独立的 `live:*` 临时状态，再按 DB 的 `commerce_incremental:*` 日检查点逐日追赶已过 02:00 的缺日；每轮最多追赶 `--max-catchup-days` 天。当天只用单轮列表与捕获键核对，不每 30 分钟创建 Excel 任务；当日跨页重叠 ID 去重并报告，日终结算仍做导出 `totalRows` 核对且保持严格重复检查。销售流水→商品行映射在两条流均成功后运行，当日尚无订单头的流水记 `partial` 并在下轮补齐，日终要求零未关联。新小时服务持有终身服务锁，每轮采集与页签补采共用工作锁；旧 worker 的进程表检查是尽力而为的第二道防线，不能阻止中途新起的 worker。源 gate 和每流 DB 锁继续限制请求与同流写入，旧日常 supervisor 未暂停时拒绝启动。

部署顺序（持有 DB 口令的交互终端执行；`plan` 不请求科迈）：

`migrate` 对应的建表已在生产 DB 用 `mycli` 执行；以后重复执行是幂等的。执行 `once` 前仍需核对旧日批、批次编排器与历史 worker 均无在途源任务。新服务当前由 `kemai_live_service.py` 启动、停止和查看状态，进程异常退出后的外部守护与开机自启尚未配置；断点保留在 DB。当前状态页已发布，浏览器视觉验收尚未执行。

采购三条流、历史收货、商品主数据和页签**尚未接入该半小时轮询器**。交易预测先以零售订单与销售流水为第一阶段；其他流应按下文分别验证小时过滤能力和实际耗时后接入独立节奏。不能把首阶段称为六流均达到 30 分钟新鲜度。

## 目标与时间口径

- **每 30 或 60 分钟触发一次**交易增量；不等到次日 02:00 才首次采集。02:00 只作为前一自然日的**结算/复核时间门槛**，可依据真实延迟数据调整。
- 每条流独立保存“最后成功采集到的源时间窗口”“最近一次实际落库时间”“最近失败/限流原因”和“积压时长”。客户页面分别展示采集新鲜度和历史完整度，不能把“任务刚执行”当成“数据已追到当前”。
- 停机、认证过期、数据库故障或限流之后，从数据库中**最后提交的窗口**自动推导未覆盖范围；不依赖“停了多久”的人工输入，也不靠进程状态 JSON 猜断点。
- 每个窗口只在源读取、稳定键去重、总量校验（源支持时）、数据库写入和事件记录均成功后推进检查点。失败保留原断点；重复执行用稳定键 upsert，不能产生重复业务行。

## 当前接口能力与约束

`kemai_opencli/utils.js` 的六类列表命令目前只接受 `YYYY-MM-DD`。零售接口内部使用 `saleTimeFrom/saleTimeTo`，技术上可能支持更细时间，但还未对真实源验证。采购使用 `operDateFrom/operDateTo` 和 `dateType`；不能假定它支持小时过滤或按修改时间过滤。商品增量脚本每轮仍扫描全量约 18,390 个商品（184 页），变化页签上次 142 商品 × 14 类用了约 75 分钟。

因此第一阶段用**按日期快照 + 差异 upsert**满足交易准实时：当天每次轮询重新读取当天列表，已存在的 ID 按版本/哈希更新，新 ID 插入；昨天和更早的未完成日按断点逐日补。当天反复读取是现有日期接口实现 30 分钟新鲜度所必需的工作，不能算历史补采的“第二轮核对”。每轮都要记录源请求数与延迟，若实际耗时超过触发周期，下一次触发合并为待办，不并行开第二个源执行者。

第二阶段验证并实现真正的时间窗接口：先离线确认 UI 请求参数及响应的边界语义，再用小窗口对比整日结果，确认无漏单、重复、跨秒边界和迟到更新后才切换。若只有业务时间过滤、没有更新时间过滤，仍须定期复核最近日期；业务发生在昨天、今天才入库的记录不会被“只扫今天”发现。

## 状态模型

按 `tenant_id + stream` 保存两条独立进度：

1. **临时窗口游标** `ingested_until`：已成功读取并提交到哪个时间点，允许当天多次前进；同时记录 `last_success_at`、`last_attempt_at`、`last_error`、`source_rows`、`saved_rows`、`verification_method` 和 `coverage_level=provisional`。这不是日终完成证明。
2. **已结算源日** `finalized_through`：与现有 `commerce_incremental:<kind>` 日期检查点衔接。只有满足日终复核条件才推进；`sync_coverage_gaps` 继续记录采购附属数组、零售原详情/支付等字段缺口。日期检查点前进不代表所有详情已完整。

首阶段新建每流一行的 `sync_live_cursors`，以 UTC `DATETIME(3)` 存当天快照开始时间和提交时间；日终仍用原 `sync_checkpoints`。每次尝试写 `sync_stream_events`，`live:*` 状态行在临时快照期间保持 `covered_through=NULL`，避免把今天误示为已结算源日。页面本地源码增加“当日同步距今”，完整的精确 `[from,to)` 水位与历史缺口聚合仍属后续时间窗接口/页面升级。现有 `sync_stream_status.covered_through` 是 `DATE`，不能直接复用为小时水位。

## 每次触发的调度算法

1. 先拿**全局单实例执行锁**，读 DB 游标、源 gate 冷却和当前时间（Asia/Shanghai）。如上一轮仍在跑，只合并触发，不新增并发；如仍在 30 分钟冷却，记录 `cooling` 与预计恢复时间，不推进游标。
2. 对每条流从 `last_successful_window_end` 推导积压。**有可靠时间过滤**时，积压按连续窗口切分；长停机可合并老窗口为 6 小时或自然日，最近窗口保持 30 分钟。**只有日期过滤**时，对每个完全遗漏的自然日只扫一次，再扫当前日；无需为 48 小时停机补 96 次半小时扫描。
3. 优先保证零售流水、零售订单等预测核心流的新鲜度；历史积压按最老未完成日有界追赶。各流独立游标，某流失败不阻塞其他流，但所有源请求仍串行且共享 0.5 次/秒 gate。商品基础详情与页签作为低优先级队列，不强行要求每半小时完成 14 类页签。
4. 同一源日的重复快照按源稳定 ID upsert，并比较版本或 payload 哈希。源列表暂时未见的旧 ID只记待核，不直接删除；分页重复键、列表总数不符或数据库写入失败时，该窗口不推进。
5. 在日终门槛后复核前一日：零售优先用导出 `totalRows` 与已保存唯一键数核对；数字一致可结算，不固定再扫第二遍。数字不同才进入受控旧日对账。采购列表的 `totalRecord` 已证实不可靠，只能给出单轮唯一键/捕获/落库一致的有限结论，并安排低频近期日期复访以发现迟到与修改。

设 `now` 为当前时刻，`cursor` 为该流最后**成功提交**的窗口终点，积压约为 `now - cursor`。状态页显示这个差值；任务失败后差值自然增长。不得用最后尝试时间替代游标，也不得在源列表成功但详情/写入失败时跳过窗口。

## 实施顺序与验收

1. **先做离线能力调查**：逐流记录是否支持小时范围、更新时间条件、可靠总数、最大可查历史；为 OpenCLI 加可选时间参数前先验证边界。未知能力按日期模式处理。
2. **新增小时游标与运行状态**：数据库迁移、只读计划命令、状态页字段。迁移不得重写现有日检查点；初始游标从已有日检查点的次日 00:00 起算，并在切换前核对六条流。
3. **实现 `plan / once / supervise`**：`plan` 不访问科迈，列出每流预计日期/时间窗与请求上限；`once` 执行有界批次；`supervise --interval-minutes 30|60` 只保持单实例，失败后从 DB 游标续跑。认证失败停下对应流并告警，限流冷却 30 分钟，数据库故障不推进游标。
4. **隔离商品慢任务**：交易高频轮询先上线；商品全清单按独立周期做差异扫描，变化详情/页签采用有界队列续跑。客户页面分别显示商品清单、详情与页签的新鲜度。
5. **灰度验收**：先离线测试 30 分钟断电、跨午夜、连续两天停机、限流、数据库写入后进程崩溃、同日重试、迟到记录、零源行与分页变化。再在单执行者下对一个真实窗口做小规模核验；比较源总数/唯一键/DB 数/检查点/状态页，确认不重复、不跳过。确认后才接管旧 supervisor，旧日常进程保持停止。
